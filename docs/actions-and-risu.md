# 상태 규칙과 Risu 실행

2026-10-19. 일반 작품의 간단한 규칙과 가져온 작품의 원본 계산을 서로 다른 실행기로
처리하되, 결과는 기존 `Room.current`와 사건별 체크포인트 한 곳에 저장합니다.

## 새 작품의 행동

제작 → **고급설정 → 이벤트**에서 이벤트·상태값·아이템·연출·상태창 다섯 탭으로 정의하고 연결합니다.

- **상태값**: 초기값·범위와 AI에게 전달할 증감 지침·구간 설명.
- **이벤트**: 이름을 붙이고 블록형/노드형으로 시작 시점·조건·순서가 있는 작업을 조립합니다. 기존 actions와 ID를 그대로 사용합니다.
- **아이템**: 초기 소지·수량·이미지·설명과 강화 비용·대상·확률을 설정합니다.
- **연출**: 자동연출(표식/문자/정규식)과 수동연출(코드·리소스·버튼·검사)을 모두 사용합니다.
- **상태창**: 같은 상태값을 참조하는 이름·선택 값·Markdown/HTML 화면을 여러 개 생성.

상태 관련 기능은 이벤트 메뉴 안의 다섯 탭에 모여 있습니다. 숫자 변경은
숫자 입력을 기본으로 하고 계산식 사용을 고르면 기존 산술 파서를 사용합니다. 편집 방식만
단순화하며 `Work.statuses/actions`와 `Runtime.status`의 계산·저장 경로는 유지합니다.
자동연출의 표식/문자 모드는 정규식 이스케이프를 자동으로 처리합니다. 실행 데이터는 기존
pattern/flags/replacement 한 벌이며 별도의 중복 설정이나 데이터 이전은 필요하지 않습니다.

상태창을 여러 개 만들어도 `Runtime.status`에 값이 복제되지 않습니다. `work.statusPanels`는
표시 설정만 저장하며 모든 창이 해당 시점의 같은 체크포인트를 읽습니다. 이전 파일에 이
필드가 없으면 기존 `statusTemplate`을 하나의 상태창으로 읽고, 여러 창을 편집하기 전까지
저장 구조를 바꾸지 않습니다. 명시적인 빈 목록은 상태창을 표시하지 않습니다. 선택 값이
없으면 모든 상태값(나중에 추가되는 값 포함)을 사용합니다. `statusIds: []`는 선택 없음입니다.
직접 작성한 템플릿은 선택과 별개로 모든 상태값을 참조할 수 있습니다.

상태창은 상태의 초기값·범위·표시와 AI가 해석할 증감 조건·구간 설명을 정의합니다.
규칙은 같은 상태값과 아이템을 대상으로, 지정한 시점에 조건을 검사하고 계산을 실행합니다.
예를 들어 상태창에서 HP를 정의한 뒤, 규칙에서 회복약 1개 소비와 HP 20 회복을 함께
처리할 수 있습니다. 버튼 규칙은 AI 호출 없이 실행됩니다. AI 응답 후 규칙은 AI의 상태
변경을 적용한 뒤 실행되므로, 같은 수치 변경을 양쪽에 중복 지정하지 않도록 합니다.

- **언제**: 플레이어의 버튼 클릭 또는 AI 응답 완료.
- **조건**: 상태값·객관식·소지 여부·아이템 수량·강화 단계. 모두/하나 이상을 선택합니다.
- **작업**: 숫자 증감/설정, 문자/객관식 변경, 아이템 획득/소비, 배경·음악, 연출 보기.

계산식은 별도의 산술 파서로 처리합니다. `eval`이나 JavaScript를 사용하지 않습니다.
화면의 `{{HP}}`는 저장 시 `[상태ID]`가 됩니다. 기존 대괄호 입력도 계속 읽습니다. 계산 결과는 상태 최소·최대 범위로 제한하고,
수량은 정수로 검사합니다. 위에서 아래로 계산하며 중간 실패 시 한 행동 전체를 취소합니다.

```text
ActionButtons → executeAction/applyAction → 체크포인트 + action 사건 → 기존 저장 큐
AI 응답 → addResponse → after-response 행동 → 응답 후보의 체크포인트 → 기존 저장 큐
```

응답 후 행동은 리롤 때 이전 시점부터 다시 계산합니다. 버튼으로 따로 진행한 행동은
대화 로그의 독립 사건입니다. 그 뒤 과거 응답을 바꾸려면 기존처럼 분기를 사용합니다.
연출 보기는 버튼을 추가하며 자동으로 전체 화면을 열거나 응답을 가로막지 않습니다.
제작 AI 에이전트도 행동을 제안할 수 있습니다.

## 가져온 작품의 배치

| 원본 데이터                           | 제작 화면/저장 위치                              |
| ------------------------------------- | ------------------------------------------------ |
| 설정·성격·시나리오                    | 작품 개요 프롬프트                               |
| 첫 인사·대체 인사                     | 도입부                                           |
| 로어북 폴더/내용/활성 방식            | 로어북 분류·프롬프트·사용 방식                   |
| 표시 정규식                           | 연출 → 자동연출                                  |
| Lua·초기 변수·요청/응답 정규식·스타일 | 이벤트 → 이벤트 → 가져온 Risu 실행 설정 (고급) |
| 예시·후속 지침·검색 설정              | `work.risu`의 요청 설정                          |
| 전체 원본                             | `importSource` 자산. 내보내기 후에도 보존        |

복잡한 원본 Lua를 수백 개의 새 행동으로 추측해 번역하지 않습니다. 새 행동은 제작자가
직접 상태와 아이템을 연결하는 데 사용하고, 원본 계산은 Risu 실행 설정으로 보존합니다.
따라서 불러온 TRPG의 고유 상태를 XenoTale의 기본 아이템 패널에 복제하지 않습니다.
원본 상태창·소지품 화면에서 같은 값을 표시합니다.

## 실행 흐름과 저장

```text
Risu 파일 → 독립 파서 → Work + 내장 자산 → 기존 작업공간 저장
                       ↓
HTML 버튼 → 동작 이름 → Worker/Lua → JSON 상태 → action 사건 + 체크포인트
                       ↓
대화 입력 → 로어북·CBS·요청 규칙·onStart/editRequest → OpenRouter
AI 응답   → onOutput·응답 규칙 → 본문 + 상태 → addResponse → 기존 저장 큐
화면 표시 → editDisplay·CBS·표시 정규식 → 격리 HTML iframe
```

상태는 `runtime.risu`에 문자열 값으로 보관합니다. `getState/setState`의 JSON 값은
`__이름`, 일반 변수는 원래 이름을 사용합니다. 새로고침·분기·후보 선택·마지막 응답 삭제는
기존 체크포인트를 사용합니다. 최신 메시지만 버튼을 조작할 수 있고 과거 메시지는 당시
상태로 표시합니다. 스크립트가 사용자 메시지를 만들면 전송 전 입력에 넣으며 자동 전송하지
않습니다. 응답 계산 중 오류가 나도 유료 응답 원문을 보존하고 오류를 알립니다.

Lua·WASM은 가져온 스크립트가 있는 작품에서만 시작합니다. Worker는 방별로 직렬 처리하고
최대 세 개를 캐시합니다. 코드와 로어북 인덱스를 재사용하며 매 클릭마다 VM을 만들지 않습니다.
초기 화면이 보이기 전에는 실행을 미룹니다. 원본 소스·스타일·이미지 바이트를 AI에게
전송하지 않으며 필요한 게임 상태와 요청 지침만 보냅니다.

표시는 버튼 처리 중에도 기존 화면을 유지합니다. `HtmlContent.tsx`가 정제한 결과를
`components/htmlFrame.js`로 전달해 같은 문서의 변경된 노드를 갱신합니다. 입력·펼침·포커스와
패널 스크롤을 유지하며 Lua가 바꾼 값과 라디오 선택은 반영합니다. 메시지 높이는 본문에
맞추므로 긴 Risu 메시지의 기본 스크롤은 대화 영역이 담당합니다. 원본 설정 패널처럼
자체 스크롤을 가진 구성은 유지합니다. 일반 자동연출의 허용 스크립트 실행은 기존 경로를 씁니다.

## 격리와 지원 범위

Lua는 Wasmoon의 Lua 5.4 WASM에서 실행합니다. JSON 외의 JS 객체를 넘기지 않고
파일·네트워크·브라우저 저장소·API 키를 연결하지 않습니다. Lua 메모리 96MiB,
함수 시간 4초, Worker 대기 10초 제한을 둡니다. 표시 HTML은 별도 출처 권한 없이
정제·CSP·sandbox를 적용하며, 앱이 넣은 버튼 전달 코드만 기본 실행합니다.
이는 원본 모든 코드의 안전성이나 Risu 전체 API 호환성을 증명하는 기능은 아닙니다.

지원하는 핵심 API는 채팅 변수/JSON 상태, 대화 읽기·본문 변경·메시지 추가,
로어북 이름 조회, 버튼 콜백, `onStart/onOutput`, `listenEdit`의 요청·표시 처리입니다.
CBS는 중첩 when/if/else, 기본 비교·논리 조건, 사용자/캐릭터명·변수·메시지 위치·버튼을
지원합니다. 알 수 없는 표현은 버리지 않습니다. 정규식은 순서·단계·캡처 치환을 따릅니다.

제한은 다음과 같습니다.

- `module.risum`, 가상 스크립트, Lua 외 트리거, 외부 API 요청, 스크립트의 추가 AI 호출은 미지원.
- `async`는 동기 콜백만 지원. 임의의 비동기 Risu 플러그인을 실행하지 않음.
- 로어북의 상시/키워드/참조, 스캔 깊이·재귀 검색은 지원. 복합 보조 조건·우선순위·정확한
  Risu 토크나이저 예산은 미지원이며 문자 수를 보수적인 예산으로 사용.
- CSS의 고정 위치는 원본 화면 iframe 안에 한정. 앱 사이드메뉴를 원본 코드가 대체하지 않음.
- 복잡한 원본 UI는 소설 모드에서 확인. 비주얼노벨의 페이지별 텍스트박스는 전체 TRPG 패널과
  같은 공간을 제공하지 않음.
- 이전 버전에서 변환한 파일은 원본 PNG를 새 작업공간으로 다시 가져와야 실행 설정이 생김.

## 검증

단위 검사로 안전한 계산식, 원자적 소비·회복, 리롤·분기, 상태 커밋 충돌, 대화 변경,
CBS·로어북 검색과 Lua의 호스트 접근 제한을 확인합니다. 사용자 제공 PNG는 저장소에
복사하지 않습니다. `RISU_EXAMPLES_DIR`를 지정한 실행에서 원본 캐릭터 생성 완료,
원본 설정창·게임 상태/주사위 주입, 시간·화폐·아이템 판정과 몬스터 전투 시작을 검사합니다.

Playwright는 PC·모바일의 행동 편집/실행/저장 복원, 원본 스타일·캐릭터 생성 선택,
실제 대화방의 모의 API 요청/응답과 설정창 복원을 확인합니다. 이 검증은 모델 비용을
사용하지 않으며 장기 캠페인과 모든 주문·상점·전투 조합의 전수 검사는 아닙니다.

의존성 `wasmoon`은 MIT입니다. `json.lua`의 rxi MIT 저작권·라이선스는 파일에 유지합니다.

## 제노테일 게임 화면

이벤트 → 상태창 → **캐릭터 만들기 예시 추가**로 코드 없는 3단계 선택 화면을 만듭니다.
종족·클래스·제작 단계·HP와 버튼 규칙을 새 ID로 함께 생성하며 기존 설정을 덮어쓰지 않습니다.
영역 제목/설명, 표시 조건(all/any), 1~3열 버튼 배치와 버튼별 실행 규칙을 수정할 수 있습니다.
설명의 `{{상태값 이름}}`은 편집 시 이름으로 보이고 저장 시 안정적인 ID 참조를 유지합니다.

`work.statusPanels[].blocks`는 화면 설정입니다. 선택 상태를 별도 저장하지 않고
`Runtime.status/inventory`를 읽습니다. 버튼의 세부규칙이 같은 값을 설정한 상태면 선택 색상을 표시합니다.
`buttonLocation: screen`인 규칙은 입력창 위의 기본 버튼을 숨깁니다. 연결을 삭제하기 전에는
해당 규칙을 삭제할 수 없으며, 게시/파일 읽기 시 버튼과 표시 조건의 참조를 검증합니다.

게임 화면은 소설 모드 도입부 영역, 비주얼노벨의 상태창 레이어, 제작 서포터의 대화 테스트에서
현재 체크포인트를 사용합니다. 편집 미리보기의 실행은 임시 상태만 변경합니다. 실제 대화의
버튼 실행은 기존 executeAction → 체크포인트 → 저장 큐를 사용하므로 AI 호출 없이 반영됩니다.
새로고침·파일 내보내기/가져오기·분기에도 같은 상태를 사용하며 이후 AI 요청에 현재 값이 포함됩니다.

### 수동연출에서 규칙 실행

연출 → 수동연출의 **연결할 이벤트**에서 허용 목록을 선택하고 **이벤트 실행 버튼 넣기**를
사용하면 코드 입력 위치에 실행 버튼을 넣습니다. 코드 사용자는 아래 API를 사용할 수 있습니다.

```js
await XenoTale.ready;
const context = await XenoTale.action('등록한 규칙 ID');
// context.status / inventory / nodeId: 변경 후의 현재 값
```

호스트는 허용 목록, 버튼 트리거, 규칙 조건, 검사 통과 여부, 현재 장면을 확인합니다.
격리 화면에 앱 저장소나 임의의 상태 쓰기 권한을 주지 않습니다. 실행은 기존 atomic action을
그대로 사용합니다. `effectOrigin`을 사건에 기록하여 같은 연출의 연속 규칙 실행 후에도
결과 확정을 허용하지만, 다른 행동/응답 뒤의 과거 연출이나 결과 확정 후에는 쓰기를 거절합니다.
미리보기는 복사된 상태만 변경합니다. 규칙의 즉시 변경을 AI 델타로 다시 적용하지 마세요.

이 변경은 새 작품의 제작 기능입니다. 기존 Risu Lua를 이 화면 설정으로 자동 변환하지는 않습니다.
기존 Risu 호환 실행과 원본 스크립트는 그대로 유지합니다.

## 통합 이벤트 편집기

숫자 증감/설정·문자/객관식 설정·획득/소비·표면/내면 관계 변경·배경·음악·연출 버튼을 조립합니다.
시나리오·내면 조건 연결은 원본 chapters/innerUnlock를 읽고 씁니다. 연결만으로 장면 이동이나 조건 우회가 발생하지 않습니다.
노드 연결은 순차 작업을 재배치하고, 블록형의 위/아래 이동과 같은 steps를 편집합니다. 두 화면 간 변환 손실은 없습니다.
자동 실행은 AI 델타·버튼·강화에서 발생한 획득/상태 변화를 같은 체크포인트 안에서 처리합니다.
각 이벤트를 트랜잭션당 한 번으로 제한해 순환을 방지하며, 실패한 자동 이벤트의 작업은 통째로 취소하고 사유를 기록합니다.
